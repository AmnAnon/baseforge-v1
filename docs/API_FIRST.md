# BaseForge API-first foundation



## Phase 2: Agent context and canonical entity resolution

### Context query

`POST /api/v1/context/query` accepts a protocol name, slug or canonical ID and returns a selected context bundle.

Request:

```json
{
  "entity": {
    "type": "protocol",
    "id": "aerodrome",
    "network": "base"
  },
  "include": ["overview", "tvl", "risk", "whales"]
}
```

Supported context sections:

- `overview`: canonical entity identity and provider metadata
- `tvl`: Base TVL and provider-reported 24h/7d/30d changes
- `risk`: BaseForge heuristic health/risk score and factors
- `whales`: indexed large-wallet events when available

### Entity identifiers

Protocol identifiers use the stable network-scoped form `protocol:base:{slug}`. The resolver accepts provider slugs, protocol names and canonical IDs. Partial matches return candidate choices instead of silently selecting one. The initial resolver covers protocols with positive reported Base TVL; token, wallet, contract and transaction entity types are future extensions.

### Provenance and quality

Each context section includes its source, observation time, age/freshness and a quality classification. Risk is explicitly labeled as a BaseForge-derived heuristic. Whale event coverage is labeled as indexed data and may be partial or unavailable when providers do not return matching events.

The query endpoint accepts public requests and optional `X-API-Key` authentication. It applies the existing IP rate limiter and records usage for authenticated keys.

### Current scope limitations

- The first context builder supports protocol entities on Base only.
- Historical time-series context and cross-entity relationship traversal are not yet included.
- The resolver uses the provider-backed protocol directory; it is not yet a general token/address registry.

## Phase 1: Discovery and contract foundations

The first API-first milestone adds a stable, machine-readable discovery surface without changing existing dashboard or legacy API contracts.

### Discovery endpoints

All endpoints below are versioned under `/api/v1` and return a `data` + `meta` envelope, except the OpenAPI document.

| Endpoint | Purpose |
|---|---|
| `GET /api/v1` | API entry point and discovery links |
| `GET /api/v1/capabilities` | Registered capability and operation catalog |
| `GET /api/v1/catalog` | Supported networks and data domains |
| `GET /api/v1/metrics` | Metric definitions, units, sources, calculations and limitations |
| `GET /api/v1/openapi.json` | OpenAPI 3.1 discovery specification |

### Response envelope

```json
{
  "data": {},
  "meta": {
    "apiVersion": "1.0.0",
    "generatedAt": "2026-10-31T00:00:00.000Z",
    "requestId": "request-id"
  }
}
```

The request ID is echoed from `X-Request-Id` when supplied (bounded to 128 characters) or generated by the server. Responses include `X-API-Version` and `X-Request-Id` headers.

### Compatibility policy

- Existing `/api/*` endpoints remain available.
- New stable contracts are introduced under `/api/v1/*`.
- Legacy endpoints are described in the capability registry but retain their current response formats.
- A legacy endpoint is not considered fully normalized until it is wrapped or replaced by a versioned adapter.
- Discovery metadata is sourced from `src/lib/intelligence/api-registry.ts`.

### Data interpretation

- Missing values are not zero.
- Provider-reported, derived and estimated values must not be conflated.
- Health and risk scores are BaseForge heuristics, not security audits, guarantees, or investment advice.
- Consumers should retain metric source, calculation and limitation metadata when displaying or reasoning over results.

### Not included in Phase 1

The context query endpoint, canonical entity resolver, provenance/freshness engine, MCP adapter changes, SDKs, API-key scopes and persistent quota accounting are subsequent milestones.

## Phase 3: Agent interoperability and SDKs

### MCP server

The Node.js and Python stdio MCP servers expose discovery and context operations as tools:

- `get_api_capabilities`
- `get_data_catalog`
- `get_metric_definitions`
- `search_protocols`
- `get_protocol_context`

The existing BaseForge tools remain available. Read-only MCP resources are exposed at:

- `baseforge://capabilities`
- `baseforge://catalog`
- `baseforge://metrics`

The context tool calls the versioned API rather than reimplementing protocol resolution or risk calculations. MCP responses preserve the API envelope and provenance metadata.

### SDKs

- Python SDK version 0.3.0: synchronous and asynchronous discovery methods plus protocol context queries.
- TypeScript SDK source: `packages/typescript`, with discovery methods, context queries and structured `BaseForgeApiError` exceptions.

Both SDKs retain the `data/meta` envelope. The TypeScript package is source-controlled in this repository and is not claimed to be published to npm yet.

### Agent skill

`docs/AGENT_SKILL.md` provides reusable agent instructions covering discovery, entity resolution, provenance, quality, ambiguity handling and safety.

### Interoperability policy

MCP and SDKs are adapters over the same versioned REST contract. They must not duplicate provider ingestion, metric calculations or risk methodology.


## Phase 4: Security, quotas and developer usage

### API key enforcement

The existing admin API key management endpoints remain the key lifecycle surface. Production per-key limits now use the shared Postgres rate-limit store rather than process-local counters. The limiter fails closed when the shared store is unavailable.

Initial rolling 24-hour quotas are configured by tier:

| Tier | Requests per 24 hours |
|---|---:|
| Free | 1,000 |
| Pro | 20,000 |
| Enterprise | 100,000 |

The existing per-minute limit remains configurable per API key. Successful authenticated responses include `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`, `X-Quota-Limit`, `X-Quota-Remaining` and `X-Quota-Reset`.

### Per-key usage

`GET /api/v1/usage` requires `X-API-Key` and returns only the authenticated key's own usage totals, latency, endpoint distribution, status breakdown and quota state. The Node.js and Python MCP servers expose this as `get_my_api_usage` and the authenticated `baseforge://usage` resource. Both SDKs expose `getUsage()` / `get_usage()`.

### Honest telemetry

The public aggregate usage endpoint no longer fabricates baseline request counts, client adoption or success rates when the database is empty. Empty databases return real zero/empty values; database failures return HTTP 503 with an unavailable status.

### Current scope boundary

API-key scopes and subscription billing are not added in this phase because the current key schema does not yet contain scope or billing fields. Adding those requires a separately reviewed database migration and policy model. The current tiers enforce request limits only.
